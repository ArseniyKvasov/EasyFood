# Уведомления: почта, push и напоминания

Техническое описание трёх каналов BiteBalance. Документ для реализации, не для пользователя.

## Принципы

1. **Разные работы у разных каналов.** Почта возвращает и объясняет, push напоминает в моменте, интерфейс ведёт к действию.
2. **Один реестр согласий.** Маркетинг по почте, push и аналитика — отдельные согласия. Отзыв одного не ломает остальные.
3. **Транзакционное отдельно от маркетинга.** Чеки, отчёты и письма-подтверждения не подчиняются маркетинговым лимитам и не отключаются вместе с рассылкой.
4. **Лимит внимания.** Не больше одного маркетингового касания в сутки на пользователя суммарно по всем каналам и не больше трёх в неделю. Тихие часы 22:00–08:00 по местному времени.

## 1. Схема данных

```sql
-- Согласия: отдельная строка на канал
create table user_consents (
  user_id       bigint not null references users(id) on delete cascade,
  channel       text   not null check (channel in ('email_marketing','push','analytics')),
  granted       boolean not null,
  source        text   not null,          -- 'signup', 'settings', 'import'
  ip            inet,
  updated_at    timestamptz not null default now(),
  primary key (user_id, channel)
);

-- Подписки на push: у одного пользователя может быть несколько устройств
create table push_subscriptions (
  id          bigserial primary key,
  user_id     bigint not null references users(id) on delete cascade,
  endpoint    text   not null unique,
  p256dh      text   not null,
  auth        text   not null,
  user_agent  text,
  created_at  timestamptz not null default now(),
  last_ok_at  timestamptz,
  revoked_at  timestamptz
);

-- Напоминания: пользовательские, не маркетинговые
create table reminders (
  id         bigserial primary key,
  user_id    bigint not null references users(id) on delete cascade,
  label      text   not null,             -- 'Завтрак', 'Обед', 'Ужин', 'Своё'
  time_of_day time   not null,
  days_mask  smallint not null default 127, -- биты пн..вс
  enabled    boolean not null default true,
  tz         text   not null,
  created_at timestamptz not null default now()
);

-- Журнал событий: источник сегментов
create table events (
  id       bigserial primary key,
  user_id  bigint references users(id) on delete cascade,
  name     text not null,
  props    jsonb not null default '{}',
  ts       timestamptz not null default now()
);
create index on events (user_id, ts desc);

-- Очередь исходящих: и почта, и push
create table messages (
  id           bigserial primary key,
  user_id      bigint not null references users(id) on delete cascade,
  channel      text not null check (channel in ('email','push')),
  kind         text not null,             -- 'welcome', 'digest', 'paywall_offer', 'reminder'
  template     text not null,
  payload      jsonb not null default '{}',
  scheduled_at timestamptz not null,
  sent_at      timestamptz,
  status       text not null default 'pending', -- pending|sent|failed|skipped|cancelled
  idempotency  text not null unique,
  attempts     smallint not null default 0
);
create index on messages (status, scheduled_at);

-- Доставка: результат от провайдера
create table deliveries (
  id          bigserial primary key,
  message_id  bigint not null references messages(id) on delete cascade,
  provider_id text,
  event       text not null,              -- delivered|open|click|bounce|spam|unsub
  ts          timestamptz not null default now(),
  meta        jsonb
);
```

## 2. Планировщик

Один воркер, раз в минуту:

1. Выбирает `messages` со `status='pending'` и `scheduled_at <= now()`.
2. Для каждого сообщения проверяет: согласие на канал, тихие часы в часовом поясе пользователя, суточный и недельный лимит, `last_seen_at` (если человек в приложении прямо сейчас — push откладывается на 30 минут), отсутствие дубля по `idempotency`.
3. Отправляет, пишет `sent_at` и `provider_id`.
4. При ошибке — до трёх повторов с интервалом 5, 30 и 120 минут, затем `status='failed'`.

Идемпотентность: ключ вида `user:123:digest:2026-11-23`. Повторный запуск воркера не отправит письмо дважды.

## 3. Почта через SMTP.bz

SMTP.bz закрывает доставку, статистику и отписки, но не хранит наши сегменты и не умеет в наши события. Поэтому решение о том, кому и когда писать, принимает наша база, а сервис только отправляет.

**Домен**

- отдельный поддомен `mail.bitebalance.ru`, чтобы репутация рассылок не влияла на транзакционные письма;
- SPF, DKIM, DMARC (`p=none` на старте, затем `quarantine`, затем `reject`), обратная DNS;
- два потока: транзакционный (`no-reply@`) и маркетинговый (`mail@`), разные отправители, лучше разные IP;
- прогрев 2–4 недели: первые дни 50–100 писем в сутки, только активным пользователям.

**Отправка**

- быстрые письма (чек, подтверждение) — сразу через API;
- рассылки — через SMTP с небольшой задержкой между письмами, чтобы не ловить троттлинг;
- заголовки: `List-Unsubscribe: <https://.../u/{token}>`, `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, `Precedence: bulk` для маркетинга;
- ссылка отписки работает без входа в аккаунт, по подписанному токену.

**Обратная связь**

Вебхуки сервиса о доставке, открытии, клике, отписке и жалобе кладутся в `deliveries`. Жёсткие отказы (5xx) сразу попадают в suppression list, повторно на этот адрес не пишем. Мягкие отказы — до трёх попыток.

**Шаблоны**

MJML → HTML. Тёмная тема, ширина 600 px, preheader, alt-тексты, обязательный текстовый вариант. Переменные: имя, норма, стрик, число записей за неделю, дата последнего визита.

## 4. Push

**Транспорт.** Web Push с VAPID. Для Android и Chrome — напрямую или через FCM. На iOS push работает только в приложении, добавленном на главный экран (iOS 16.4+), поэтому канал проверяет `display-mode: standalone`.

**Ключи и подписка.** Пара VAPID на сервере, публичный ключ в фронтенде. Подписка сохраняется в `push_subscriptions` с endpoint, p256dh и auth. Ответ 404 или 410 при отправке означает, что подписка мертва: помечаем `revoked_at` и удаляем через 30 дней.

**Payload**

```json
{
  "title": "Обед не записан",
  "body": "Две минуты — и день снова в норме",
  "icon": "/icons/192.png",
  "badge": "/icons/badge.png",
  "tag": "meal-reminder",
  "data": { "url": "/?open=add&mode=photo" }
}
```

`tag` схлопывает одинаковые уведомления, `renotify` не используем, чтобы не звенеть повторно.

**Разрешение.** Сначала свой экран-объяснение («Напоминать про обед? Одно уведомление в день»), системный запрос — только после нажатия «Включить». Триггер: первая запись или второй день использования. Не спрашиваем при первом открытии: отказ в системном диалоге почти необратим.

## 5. Напоминания

Пользовательские напоминания не подчиняются маркетинговым лимитам. До трёх на Free, до шести на Plus.

**Расчёт времени.** Храним локальное время и часовой пояс. При каждом запуске воркер считает ближайший момент в UTC с учётом перехода на летнее время (в РФ его нет, но пользователи бывают в других зонах). Пропущенные из-за простоя запуски не догоняем: напоминание про обед в 23:00 бессмысленно.

**Умная тишина.** Перед отправкой проверяем, не заполнен ли день: если завтрак уже записан, напоминание про завтрак не уходит. Если день закрыт целиком, не уходит ничего.

**Подстройка.** Медиана времени записей за 14 дней сдвигает напоминание: если человек стабильно записывает обед в 14:20, напоминание в 13:00 переезжает на 13:45. Сдвиг не больше 60 минут и только после семи записей.

**Без разрешения на push.** Напоминание живёт в интерфейсе: баннер в дневнике в нужное время и бейдж на иконке, если приложение установлено. Email-дубль не отправляем.

**Где спрашиваем время**

1. Сразу после первой записи: «Напомнить завтра про обед?» Время подставляется по текущему приёму пищи.
2. В настройках, раздел «Напоминания»: три переключателя, поля времени, своё напоминание.
3. На экране установки на главный экран: на iPhone это единственный способ получить push.

## 8. Юридические рамки

- email и push-токен — персональные данные, нужны согласие и политика;
- маркетинговые сообщения — реклама по статье 18 закона «О рекламе»: согласие и отписка в каждом сообщении;
- напоминания и чеки — не реклама, отзыв маркетингового согласия их не отключает;
- тихие часы и лимиты — не только вежливость, но и снижение жалоб;
- при удалении аккаунта удаляются подписки и напоминания, кроме платёжных документов.

## 9. Порядок работ

1. Таблицы и журнал событий.
2. Воркер с лимитами и тихими часами.
3. Транзакционные письма и чеки.
4. Напоминания (модель, настройки, отправка).
5. Push: ключи, service worker, экран разрешения.
6. Маркетинговые цепочки на почте.
7. Сегменты и реактивация.
